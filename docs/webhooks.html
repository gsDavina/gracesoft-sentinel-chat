Webhooks & endpoints

Every HTTP route exposed by concierge-service, cook-service, demo-service and assistant-service. All four expose the identical set of routes — only the agent behind them differs. Channel mounting lives in one shared package, @gracesoft-sentinel/webhook-host.

Every channel can run at once. Each enabled channel gets its own path — /whatsapp/webhook, /telegram/webhook, /sms/webhook, /slack/webhook, /line/webhook, plus the web chats at /chat/gracesoft/ and /chat/davdevs/ — so any combination of *_ENABLED flags works on one process. At least one must be on. Register the per-channel path with each platform for new setups.
Legacy /webhook still works. Before per-channel paths, every router claimed the same /webhook — so with WhatsApp and Telegram both enabled, WhatsApp's router rejected every Telegram delivery. The shared path is kept for already-registered webhooks (e.g. the live Railway deployments): each request is routed by the platform's own signature header (X-Hub-Signature-256, X-Telegram-Bot-Api-Secret-Token, X-Twilio-Signature, X-Slack-Signature, X-Line-Signature), and a POST carrying none of them gets 403, as before. WhatsApp's GET handshake is answered there too.
Webhook routes are rate limited to 120 requests per minute per source IP (a floor against flooding — webhook traffic comes from each platform's own servers). The web chats' message endpoint is limited to 30 per minute per IP, since that traffic is end users. Over the limit: 429.

Health & readiness

GET/health

Always 200 once the process has started — a liveness check, not a dependency check.

{ "status": "ok" }
GET/ready

Pings Redis and Postgres. Returns 200 only if both respond; 503 otherwise. Point your orchestrator's readiness probe here, not at /health.

200  { "status": "ready" }
503  { "status": "not ready" }

WhatsApp

Active only when WHATSAPP_ENABLED=true. Requires WHATSAPP_PHONE_NUMBER_ID, WHATSAPP_ACCESS_TOKEN, WHATSAPP_APP_SECRET, and WHATSAPP_WEBHOOK_VERIFY_TOKEN.

GET/whatsapp/webhook

The one-time verification handshake Meta performs when you register the webhook URL in the WhatsApp Business Platform console. Meta calls this with:

GET /whatsapp/webhook?hub.mode=subscribe&hub.verify_token=YOUR_TOKEN&hub.challenge=1234567

If hub.mode=subscribe and hub.verify_token matches your configured WHATSAPP_WEBHOOK_VERIFY_TOKEN, the server echoes hub.challenge back with 200. Otherwise it returns 403.

POST/whatsapp/webhook

Receives inbound message/status payloads from the WhatsApp Cloud API. Every request must carry a valid X-Hub-Signature-256 header — HMAC-SHA256 of the raw request body, keyed by WHATSAPP_APP_SECRET, hex-encoded and prefixed sha256=. A missing or invalid signature gets 403.

On a valid signature, the server responds 200 immediately (Meta expects an ack within a few seconds and retries otherwise), then asynchronously: normalizes the message, runs it through the agent, formats the reply for WhatsApp, and sends it back via the Cloud API's own send-message endpoint. Status-update pings (delivery receipts etc., no messages array) are acknowledged and dropped — nothing is sent to the agent for those.

Telegram

Active only when TELEGRAM_ENABLED=true. Requires TELEGRAM_BOT_TOKEN and TELEGRAM_WEBHOOK_SECRET. Unlike WhatsApp, Telegram has no GET handshake — you register the webhook URL yourself, once, via a direct call to Telegram's setWebhook API (passing your chosen secret token), rather than the channel initiating a handshake against you.

POST/telegram/webhook

Receives Telegram Update objects. Every request must carry X-Telegram-Bot-Api-Secret-Token matching your configured TELEGRAM_WEBHOOK_SECRET exactly (constant-time compared) — a missing or mismatched header gets 403.

Responds 200 immediately, then asynchronously normalizes, runs the agent, and replies via the Bot API's sendMessage/sendPhoto. Updates with no message or callback_query (e.g. edited-message notifications) are acknowledged and dropped.

SMS / MMS (Twilio)

Active only when SMS_ENABLED=true. Requires TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_FROM_NUMBER, and SMS_WEBHOOK_URL — the exact public URL you configure in Twilio (its signature covers the URL, which can't be reliably reconstructed behind a proxy).

POST/sms/webhook

Receives Twilio's application/x-www-form-urlencoded inbound-message POST (not JSON). Every request must carry a valid X-Twilio-Signature header: HMAC-SHA1, base64-encoded, of the exact webhook URL with each POST parameter's key+value appended in sorted-key order, keyed by your Twilio auth token — Twilio's own signature scheme.

Responds 200 with an empty <Response></Response> TwiML body immediately, then asynchronously normalizes and runs the agent. Quick replies degrade to a plain-text numbered list on this channel — the chatter replies with a number, resolved by the agent's existing free-text selection fallback.

Slack

Active only when SLACK_ENABLED=true. Requires SLACK_BOT_TOKEN (xoxb-…, scopes chat:write, plus files:read for attachments, im:history and app_mentions:read) and SLACK_SIGNING_SECRET. In the Slack app config, point both the Event Subscriptions Request URL and the Interactivity Request URL at the same path, and subscribe to message.im and app_mention.

POST/slack/webhook

Every request must carry X-Slack-Signature (v0= + HMAC-SHA256 of v0:{timestamp}:{raw body}, keyed by the signing secret) and an X-Slack-Request-Timestamp within 5 minutes — anything else gets 403. Answers the one-time url_verification challenge. Otherwise acks 200 at once and processes asynchronously.

Direct messages and @mentions reach the agent; the app's own messages, edits and other subtypes are dropped, as are Slack's automatic retries (X-Slack-Retry-Num) so a slow ack never produces a double reply. Quick replies render as Block Kit buttons (tapped buttons arrive form-encoded on the same path). Each chatter is keyed by {channel}:{user}, so two people mentioning the app in one channel keep separate conversations.

LINE

Active only when LINE_ENABLED=true. Requires LINE_CHANNEL_ACCESS_TOKEN and LINE_CHANNEL_SECRET from the LINE Developers console. Set the channel's Webhook URL to this path and turn on "Use webhook".

POST/line/webhook

Every request must carry X-Line-Signature (base64 HMAC-SHA256 of the raw body, keyed by the channel secret); otherwise 403. The console's "Verify" button (an empty events array) is acked like any delivery.

Acks 200 at once, then answers each text/media message and postback in the batch independently — standby-mode events and redeliveries are skipped. Replies use the free Reply API with the event's reply token, falling back to the Push API if the token has expired (a slow model answer can outlive its ~1-minute lifetime). Quick replies render as LINE quick-reply postback buttons (labels truncated to LINE's 20-character limit).

Branded web chats

WEB_GRACESOFT_ENABLED=true and/or WEB_DAVDEVS_ENABLED=true serve a browser chat themed to each brand, built on the @gracesoft-sentinel/web-chat-kit template (theme tokens → one shared layout). Set WEB_CHAT_ACCESS_TOKEN (8+ characters) before exposing either publicly — without it, anyone with the URL talks to a paid model, and the service logs a warning at boot. WEB_CHAT_PRODUCT_NAME/WEB_CHAT_WELCOME_MESSAGE optionally override the header and first message.

GET/chat/gracesoft/ · /chat/davdevs/

The chat page (strict Content-Security-Policy: script-src 'self', no inline script or style), plus theme.css, the template's assets/ and the brand's brand/ files beneath it. The bare path without a trailing slash redirects to it.

POST/chat/{brand}/api/messages

The page's only API. Unlike the webhooks, the reply comes back on the same response:

POST { "sessionId": "…16-64 URL-safe chars…", "text"?: "…", "quickReplyId"?: "…", "image"?: "data:image/png;base64,…" }
200  { "reply": { "text"?: "…", "quickReplies"?: [{ "id", "label" }], "images"?: ["https://…"] } }
400  { "error": "invalid_message" }      401  { "error": "access_code_required" }
413  { "error": "too_large" }            429  { "error": "rate_limited" }

sessionId is a random id the page keeps in localStorage and becomes the message's senderId. Images up to ~4 MB (PNG/JPEG/WebP/GIF). With an access code set, send Authorization: Bearer <code>.

Deleting your data

On every channel, sending /deletemydata (or "delete my data", /forgetme) starts a two-step erasure: the service replies naming exactly what will be deleted and asks for confirmation (a button, or typing DELETE) within 5 minutes; any other reply cancels it and is answered normally. On confirmation it hard-deletes the chatter's session state (Redis, or in-memory for assistant-service) and their rows in Postgres's conversation_messages/bookings tables. Appointments already on the business calendar are not removed — the chatter is told to cancel them first. A partial failure is reported as a failure, with a contact address, never as "done". The command itself is never forwarded to an agent or logged.
