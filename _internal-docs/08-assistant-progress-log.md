## 2026-09-24 — M3: LLM orchestration (tool catalog, system prompt, tool-use loop, session memory)

**Status:** M3 done and unit-tested against a scripted model. Continuing straight on to M4 in the same session.

**The core design problem:** this repo's `AIProvider` interface (`packages/core/src/ai-provider.ts`) has no function-calling/tool-use support — `chatComplete` just takes messages and returns text. Every existing agent works around this with a one-shot "respond with this exact JSON shape" prompt (`agent-cook`'s `faq-matcher.ts`). M3 needed a genuine multi-step tool-use *loop*, which doesn't exist anywhere in the repo yet, so this generalizes that same JSON-protocol convention rather than reaching for OpenAI's native function-calling (which would tie the assistant to one provider and break the `AIProvider` abstraction every other agent depends on).

**What was built:**
- `src/tools/definitions.ts` — 22 tools wrapping the M2 query layer (`get_hours_for_period`, `get_project_health`, `get_overdue_cards`, `search_cards`, etc., plus `list_projects_and_boards` so the model can sanity-check a name before answering). Every tool takes the **pseudonym** the user actually said ("Project 4"), never an internal id — the model never sees an id at all. Each tool carries its own Zod `argsSchema`; a `tool()` helper erases the per-tool `Args` generic into a uniform `{ validate(raw): ToolValidation, run(ctx, args): QueryResult }` shape so a heterogeneous array of tools type-checks without resorting to `any` (the first draft used `ToolDefinition<Args>[]` directly and hit TypeScript's contravariant function-parameter check on `run` — fixed by moving the cast inside a single contained closure per tool instead of trying to make the array itself covariant).
- `src/orchestrator/system-prompt.ts` — encodes every rule from the milestone doc's "Guiding principles" (no arithmetic, snapshot-time not wall-clock, stay inside the snapshot, pseudonyms are final, billable value ≠ income, no auto-sync between tools, read-only, answer-format), plus a prompt-injection guard modeled directly on `faq-matcher.ts`'s `PROMPT_INJECTION_GUARD` constant, and the full tool catalog rendered as text.
- `src/orchestrator/orchestrator.ts` — `runAssistant()`: the tool-use loop. Protocol is `{"action":"call_tool",...}` / `{"action":"final_answer",...}` JSON only. Each step: call the model (with a timeout + exponential-backoff retry that never throws out to the caller), parse the JSON defensively, and either execute the named tool (validating args first, feeding a corrective message back on bad JSON/unknown tool/bad args so the model can self-correct rather than the whole request failing) or return the final answer. Hits `maxSteps` → graceful "try a narrower question" message, not a crash; exhausts retries → graceful "trouble reaching the model" message, not a thrown error. `onToolCall` is a plain callback (question/tool/args/latency), not a hard dependency on `@gracesoft-sentinel/logging` — matches the existing convention that agent packages stay logging-agnostic and only apps own logging (`cook-service`'s `on-message.ts` is where that wiring actually happens); M4 will pass a callback that logs via `createLogger("assistant-service")`.
- `src/session/assistant-session.ts` — short conversation memory, built on `core`'s existing `SessionStore`/`ConversationState` (the same interface `provider-session-redis` already backs for `agent-cook`/`agent-concierge`) rather than inventing a new persistence abstraction. `loadHistory`/`appendTurn`/`resetSession`, capped to the last 10 turns so history can't grow the prompt unboundedly across a long session.
- `src/orchestrator/test-support.ts` — `ScriptedAIProvider`, a queued-response fake `AIProvider` (mirrors `provider-ai-openai`'s own mocked-fetch test convention) so the whole loop — multi-step tool calls, malformed-JSON recovery, unknown-tool recovery, bad-argument recovery, step-limit exhaustion, retry-then-fail, and session-history forwarding — is fully covered without any live model call or API key.

**What's explicitly deferred, and why:** the milestone's M3 exit criterion ("90% of the golden set passes from the command line") and most of the test checklist's "Tool selection"/"Answer correctness"/"Conversation" sections need a live model actually choosing tools and phrasing answers — that's inherently not unit-testable against a scripted fake. Recorded as unchecked-with-a-note in `08-assistant-test-checklist.md.md` rather than silently skipped; it becomes exercisable once M4's standalone service is wired to a real `OpenAIProvider` with an API key, which is the user's to provide.

**Verified locally (all green):** `pnpm --filter @gracesoft-sentinel/agent-assistant test` (94 tests total, 21 new: 8 tool-definition + 8 orchestrator + 5 session-memory), `typecheck`, `lint` — clean.

**Nothing deferred to the user for the code itself** — no live credentials used or needed for any of this session's testing.

**Next:** M4 — a minimal standalone service so the assistant can actually be run and talked to.

## 2026-09-24 — M0-M2: scaffolding, snapshot ingestion, deterministic query layer

**Status:** New package `packages/agent-assistant`. Milestones M0, M1 and M2 done and tested; M3 (LLM orchestration) is next.

**Where this fits in the existing repo:** explored `agent-concierge`/`agent-cook`, `agent-switcher`, `apps/demo-service` and `apps/cook-service` before writing anything, so this follows the repo's actual conventions rather than the milestone doc's standalone "Node/TypeScript, in line with the existing Telegram assistant" description in isolation:
- Package shape (`package.json`, `tsconfig.json` extending `@gracesoft-sentinel/config-tsconfig/library.json`, Vitest colocated `*.test.ts`) copies `agent-cook` exactly.
- The repo has **no LLM tool-calling loop anywhere** — every existing agent is a deterministic dispatcher that calls `AIProvider.chatComplete` for narrow one-shot JSON-structured asks (see `agent-cook`'s `faq-matcher.ts`). M3 will need to build a JSON-protocol tool-use loop from scratch on top of `chatComplete` — there's no native function-calling support in `AIProvider` to lean on.
- The repo has **no Anthropic provider** — only `provider-ai-openai` and `provider-ai-gemini`. The milestone doc's "Claude Haiku for cost, Sonnet as a switch" is aspirational; recorded as a resolved decision in `08-assistant-milestone.md` to reuse `AIProvider`/`OpenAIProvider` like every other agent, not add a new provider package.
- `apps/demo-service`'s multi-agent wiring is `agent-switcher`'s `RegisteredAgent { name, label, triggers, onMessage }` over plain Express webhooks — no generic `POST /chat` JSON endpoint exists today. This resolves M0's open question #1 for M5; M4's standalone service will need its own new Express (not Fastify — see below) app.

**M1 — snapshot ingestion (`src/types/`, `src/loader/`):**
- Zod schemas for every Desk entity (`Project`, `TimeEntry`, `Account`, `PaymentMethod`, `Category`, `Vendor`, `Service`, `Transaction`, `DeskDocument`) and every Skylight entity (`Board`, `Column`, `Card`, `Checklist`, `ChecklistItem`, `Comment`, `Note`, `ActivityLogEntry`). Money is integer cents (`SGD` only), durations are integer minutes, `Stage` is a 6-value enum in SDLC order.
- `loadSnapshot(dir)`: reads 17 JSON files (one per table), Zod-validates every row with the table name + row id in the error on failure, checks referential integrity (time entries → projects, transactions → accounts/methods/categories/vendors, cards → columns → boards, checklist items → checklists), builds the cross-tool pseudonym index (and warns — not errors — on either-direction mismatches), flags out-of-snapshot dates as warnings, and runs the redaction scanner (which **fails** the load) before returning.
- `scanDeskForRedactions`/`scanSkylightForRedactions` (`redaction-scan.ts`): scans only known free-text fields (notes, titles, comments, filenames, pseudonyms) — deliberately not a blind deep-walk of every string field, which would false-positive on ISO date strings looking like phone numbers. Five checks: email, URL, phone, 6+-digit account/bank number, file path.
- `resolveSgtCalendarDate`/`minutesToHours`/`sumCents` (`normalize.ts`) — the SGT day-boundary and floating-point-drift rules from the checklist, each with its own test.
- **No real Desk/Skylight export exists yet** to ingest — nothing has been handed off from the actual apps. Built a hand-crafted, internally-consistent fixture instead (`data/snapshot/valid/*.json`: 5 projects, 14 time entries, 9 transactions, 5 boards, 11 cards, a 5-item checklist, 6 activity-log entries, deliberately including one out-of-range time entry, one unmatched board, one unmatched project, one deleted card, and two prompt-injection-style strings in a comment and a transaction note) sized to exercise every bullet in the test checklist's ingestion and query sections. Negative-path tests (`test-support.ts`) mutate copies of this fixture in a temp dir rather than hand-authoring a parallel "broken" fixture per failure case.

**M2 — deterministic query layer (`src/query/`):**
- `period.ts`: `resolvePeriod` turns keywords (`today`, `this_week`, `this_month`, `last_month`, `last_30_days`, `q3`), month names, or explicit `{start,end}` into a resolution carrying `clipped`/`partial`/`outOfSnapshot` flags — all nine period-resolver checklist cases pass, including "June"/"October" correctly signaling `outOfSnapshot: true` rather than an empty range.
- `types.ts`: every query function returns `QueryResult<T>` — `{ data, sourceTool, dateRange, caveats, outOfSnapshot }` — never a bare value, so nothing downstream (M3's prompt, M4's UI) has to re-derive what range or caveats applied.
- `time.ts` (Desk time/projects): `hoursForPeriod`, `billableValueForPeriod`, `stageBreakdown`, `currentStage` (documented rule: most recent time entry by date — correctly returns Development for a project that went Testing→Development), `commitVsManualForPeriod`, `projectSummary`, `projectWithMostTimeInPeriod`.
- `finance.ts` (Desk finance): `financeForPeriod`, `cashPosition`, `pendingAndOutstanding`, `monthlySummary`, `categorySpendForPeriod`, `incomeReceivedForProject`. Decided and documented: only `status: "posted"` transactions count toward income/expense/net and account balances — pending/outstanding are surfaced only via `pendingAndOutstanding`, never silently folded into a total that implies they've cleared.
- `skylight.ts`: `overdueCards`, `cardsDueOn`, `cardsBy`, `checklistProgress`, `cardsCompletedInPeriod` (correctly excludes a card moved into Done and back out within the period — walks each card's sorted activity log rather than just checking current state), `recentActivity` (merges activity log + comments + notes, deliberately *not* filtered by `deletedAt` since deleted cards must still surface in activity history), `searchBoards`, `searchCards`.
- `cross-tool.ts`: `projectHealth` (joins by shared pseudonym; returns Skylight-only or Desk-only with a caveat when one side is missing, and declines cleanly when neither exists), `timeVsCompletionCorrelation` (always carries the "no automatic sync, correlation only" caveat).
- Two small, deliberate gaps, neither blocking any golden question: (1) `hoursForPeriod`/`billableValueForPeriod` don't yet return a *period-scoped* stage breakdown in one call — `stageBreakdown(projectId)` covers the project's whole history, which is what every checklist item and golden question actually asks for; (2) the `services` table is loaded and validated but not yet linked to `transactions` (no `serviceId` field), so "service spend" beyond category-level (SaaS) spend isn't queryable yet.

**Verified locally (all green):** `pnpm --filter @gracesoft-sentinel/agent-assistant test` (73 tests: 26 loader/redaction/normalize + 47 query layer, all hand-calculated against the fixture before being asserted, not derived from the implementation), `typecheck`, `lint` — all clean on the first full run after one bug found and fixed (`projectHealth`'s Desk figures were double-counting a date-range boundary against `projectSummary`'s all-time figures; fixed by reusing `projectSummary` directly instead of re-deriving with a separate period filter).

**Nothing deferred to the user for M0-M2** — no live credentials or hosting needed; this is pure data-modeling/query logic, fully verifiable with the fixture.

**Next:** M3 (tool definitions + system prompt + tool-use loop over `AIProvider`), then a minimal M4 (standalone Express service — deviating from the milestone doc's "Fastify" suggestion to match this repo's existing convention, recorded as a decision when it lands).
